description: Plan the next batch of features for an existing app — triage, interview, blast radius, doc updates
argument-hint: [optional one-line goal for this iteration]
---

You are in ITERATION mode. The app already exists (some features shipped);
the user wants to plan the next batch of work. Apps evolve — this command is
the sanctioned way back into the docs, so the contract keeps matching
reality instead of fossilizing as a v1 snapshot.

Preconditions — check these first and stop with guidance if unmet:

- SPEC.md must exist. If it doesn't and the codebase is non-empty, tell the
  user to run /conventions (per stack) then /refine — /refine documents the
  current state of an existing codebase before scoping new work. If the repo
  is empty, this is a greenfield project: /refine, not /iterate.
- No harness run may be active (`harness/.lock` must not exist).
- Statuses must be read from the branch that holds the truth. Gated mode:
  main. Autonomous mode: if `harness/integration` exists with unpromoted
  work, stop and tell the user to promote (or delete) it first — reading
  main while done-flips sit on the integration branch misclassifies
  everything it contains.

## Step 1 — Triage (mechanical, before any conversation)

Classify EVERY feature in `features/` and print the table:

- **done** — frontmatter `status: done` on the truth branch.
- **in-flight** — a `feat/NNN` branch exists (local or origin: check
  `git show-ref` and `git ls-remote --heads origin 'feat/*'`) or an open PR
  exists. Committed work built against the current docs.
- **parked** — `status: awaiting_human` or a `features/NNN.blocked` marker.
- **escalated** — `status: escalated`.
- **not started** — `status: pending` with no branch. Just a plan; freely
  rewritable.

This table drives everything below — a decision revision costs nothing on a
not-started feature and discards real work on an in-flight one.

## Step 2 — Interview

Same rules as /refine and /plan: ONE question at a time, skeptical, no
padding. Two threads:

1. **What's next**: the new goals for this iteration ($ARGUMENTS seeds
   this). Scope them the /refine way — what's in, what's explicitly out,
   what the smallest valuable version is.
2. **What changes**: does any new goal pressure an existing PLAN.md
   decision? For each proposed revision, CHALLENGE THE PREMISE before
   accepting it — there are three shapes, and the middle one is usually
   right:
   - **Migrate**: revise the decision everywhere (real blast radius — make
     the user say why it's worth it).
   - **Conform**: keep the decision; the new feature adapts to it (zero
     blast radius — does the new feature actually NEED the change?).
   - **Scope**: both technologies coexist for genuinely different workloads
     — a new D-record for the new subsystem, the old one untouched (rarely
     right; two queues/two auth models is usually a smell, so make the user
     defend it).
3. **Design surface** (when DESIGN.md exists): check each new goal's UI
   against it. If the batch introduces surfaces the doc is silent on (new
   component types, layout patterns, state treatments), flag a DESIGN GAP
   for the hand-off — /design's extend mode fills it before slicing. If a
   goal requires CHANGING a settled foundation (rebrand, palette, density),
   that is a design REVISION: challenge the premise like any decision
   revision, and if approved it enters the blast radius below.

## Step 3 — Blast radius (present BEFORE touching any doc)

For each approved decision revision, grep `features/` for the D# it touches
and report the consequence per triage state:

- **done** features: immutable history. The revision generates a MIGRATION
  SLICE in this batch, with preservation criteria ("messages in flight
  during cutover are not lost").
- **not started** features: their files will be regenerated by /slice
  against the revised decision. Free.
- **in-flight** features: two honest options, chosen per feature with the
  user — RESTART (branch rebuilt from base against the new docs via
  `--restart`; state the cost: "N rounds of committed work discarded") or
  DEFER (the feature finishes under the old decision, and a migration slice
  converts it later — only sensible when it's nearly done). There is no
  silent third option: an in-flight feature must never keep building while
  the contract changes underneath it (the evaluator reads docs at HEAD and
  will fail it — wastefully — if you let that happen).
- **parked / escalated** features: already waiting on the user — force an
  explicit keep / restart / drop call for each.

An approved DESIGN revision gets the same treatment: shipped screens that
would violate the new language become restyle MIGRATION SLICES (preservation
criteria: behavior unchanged, appearance updated — otherwise the app stays
permanently half-and-half), and in-flight UI slices face the same
restart-or-defer choice.

Print the full plan (new slices, migration slices, rewrites, restarts,
deferrals) and get the user's approval before step 4.

## Step 4 — Update the docs (SPEC.md and PLAN.md only)

- **SPEC.md**: fold the scope of DONE features into "Current state (as
  built)" as terse capability lines. "This iteration" becomes: carried-over
  unfinished scope + the newly agreed goals. Update "Out of scope" to match
  what was decided.
- **PLAN.md**: existing non-revised decisions are SETTLED — restate nothing,
  re-litigate nothing. Approved revisions: mark the old record superseded
  (one-line collapse, pointing at the successor) and write the successor as
  a new D-record with full options/chosen/revisit-if. New decisions from the
  interview: append as new D#s. Slice plan: append the new slices and
  migration slices (numbered after the highest existing feature), and update
  the entries for not-started slices a revision touches.
- **Feature files: DO NOT TOUCH.** /slice is the only writer of features/ —
  after review, the user runs /slice to expand and regenerate. Branches:
  also not yours; restarts happen via run.sh --restart.

## Step 5 — Hand off

End with, in order:

1. The doc diff summary — tell the user to review SPEC.md and PLAN.md.
2. `Run /design` — ONLY if a design gap or approved design revision was
   flagged in step 2; its extend mode appends the new surface rules (or the
   revised language) before slicing, so criteria can reference them.
3. `Run /slice` — expands new/updated slices into features/ (its
   incremental rules protect everything non-pending).
4. The restart list, if any: `./harness/run.sh --features <N> --restart`
   per in-flight feature the user chose to restart.
5. The run command for the batch, e.g.
   `./harness/run.sh --features-until <highest> --mode gated|autonomous`.
6. If SPEC.md or PLAN.md have grown fat with shipped history, suggest
   `/compact`.

Do not start implementing anything.
